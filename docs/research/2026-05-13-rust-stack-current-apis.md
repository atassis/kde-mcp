# Current Rust Crate APIs vs. Spec Assumptions

A read-only snapshot of the current API surface for `rmcp 1.7.0`, `reis 0.6.1`, and `atspi 0.30.0` — the three crates the spec leans on most heavily — plus a one-paragraph audit of the supporting layer (`zbus 5.15`, `notify-rust 4.17`, `portable-pty 0.9`, `fd-lock 4.0`). Captured 2026-05-13.

The spec (`docs/specs/2026-05-13-kde-computer-use-mcp-design.md`) was drafted against older versions: `rmcp 0.1`, `reis 0.4`, `atspi 0.22`. All three have moved. This note records what changed, what compiles differently, and what spec §13 module patterns should change in the implementation plan.

Sources are GitHub `main`/`master` branches and crates.io metadata. `docs.rs` was avoided because of intermittent cookie walls; the GitHub raw URLs cited inline are authoritative for the current API surface.

---

## Headline diffs

| Crate | Spec pinned | Current | Compatibility verdict |
|---|---|---|---|
| `rmcp` | `0.1` | `1.7.0` | **API rewritten**. Macro-based `#[tool_router]`/`#[tool]`/`#[tool_handler]` is the canonical surface; the spec's `ServerCapabilities` + `tools/list` hand-roll is obsolete. |
| `reis` | `0.4` | `0.6.1` | **Mostly additive**, but the convenient `handshake_tokio` + `reis::tokio::EiEventStream` async helpers (used in the spec's example sketch) only exist behind `feature = "tokio"`, and the event API is `reis::event::EiEvent`, not the raw protocol enum. |
| `atspi` | `0.22` | `0.30.0` | **Surface preserved, names mostly stable**. `AccessibilityConnection` is still the entry point. New: `root_accessible_on_registry()`, `ObjectRefExt::into_accessible_proxy(&conn)`, `ProxyExt` for sibling proxies (Component, Text, etc.). The spec's "open `atspi::AccessibilityConnection`" is still correct verbatim. |

The big substantive surprise: **rmcp 1.x is procedurally macro-heavy in a way 0.1 wasn't.** Reading the spec's §6 and §13 with current rmcp in mind, the tool modules don't need their own boilerplate routing — they need to be `#[tool]`-annotated methods on a single struct, with the router generated by `#[tool_router]`. That changes the shape of `src/tools/`.

## 1 — `rmcp 1.7.0`

### Verified facts

- **Version**: 1.7.0 (published 2026-05-13 per crates.io).
- **Repo**: https://github.com/modelcontextprotocol/rust-sdk
- **Default features**: `base64`, `macros`, `server` (workspace `Cargo.toml`).
- **Async runtime**: tokio 1.x, with `sync`, `macros`, `rt`, `time` features required.
- **Examples directory**: `examples/servers/src/{counter_stdio,memory_stdio,counter_streamhttp,prompt_stdio,task_stdio,…}.rs` with a shared `common/counter.rs` module the spec author should treat as the reference.

### The current minimal stdio server

From `examples/servers/src/counter_stdio.rs` verbatim:

```rust
use anyhow::Result;
use common::counter::Counter;
use rmcp::{ServiceExt, transport::stdio};
use tracing_subscriber::{self, EnvFilter};
mod common;

#[tokio::main]
async fn main() -> Result<()> {
    tracing_subscriber::fmt()
        .with_env_filter(EnvFilter::from_default_env().add_directive(tracing::Level::DEBUG.into()))
        .with_writer(std::io::stderr)
        .with_ansi(false)
        .init();

    let service = Counter::new().serve(stdio()).await.inspect_err(|e| {
        tracing::error!("serving error: {:?}", e);
    })?;
    service.waiting().await?;
    Ok(())
}
```

The handler — `Counter` — looks like this (lifted from `examples/servers/src/common/counter.rs`):

```rust
use rmcp::{
    ErrorData as McpError, RoleServer, ServerHandler,
    handler::server::{
        router::{prompt::PromptRouter, tool::ToolRouter},
        wrapper::Parameters,
    },
    model::*,
    service::RequestContext,
    tool, tool_handler, tool_router, schemars,
};

#[derive(Debug, serde::Deserialize, schemars::JsonSchema)]
pub struct StructRequest { pub a: i32, pub b: i32 }

#[derive(Clone)]
pub struct Counter {
    counter: Arc<Mutex<i32>>,
    tool_router: ToolRouter<Counter>,
    prompt_router: PromptRouter<Counter>,
}

#[tool_router]
impl Counter {
    pub fn new() -> Self {
        Self {
            counter: Arc::new(Mutex::new(0)),
            tool_router: Self::tool_router(),
            prompt_router: Self::prompt_router(),
        }
    }

    #[tool(description = "Increment the counter by 1")]
    async fn increment(&self) -> Result<CallToolResult, McpError> {
        let mut counter = self.counter.lock().await;
        *counter += 1;
        Ok(CallToolResult::success(vec![Content::text(counter.to_string())]))
    }

    #[tool(description = "Calculate the sum of two numbers")]
    fn sum(&self, Parameters(StructRequest { a, b }): Parameters<StructRequest>)
        -> Result<CallToolResult, McpError>
    {
        Ok(CallToolResult::success(vec![Content::text((a + b).to_string())]))
    }
}

#[tool_handler]
impl ServerHandler for Counter {
    fn get_info(&self) -> ServerInfo {
        ServerInfo::new(
            ServerCapabilities::builder()
                .enable_prompts()
                .enable_resources()
                .enable_tools()
                .build(),
        )
        .with_server_info(Implementation::from_build_env())
        .with_protocol_version(ProtocolVersion::V_2024_11_05)
        .with_instructions("…".to_string())
    }
}
```

### What this means for spec §13

The spec sketches each tool in its own file under `src/tools/`, with `mod.rs` presumably stitching them into a router. **With rmcp 1.7, the entire tool surface is a single `impl` block on a single struct** (or it must be, unless we want to fight the macros). The proc-macro `#[tool_router]` walks one `impl` and synthesises a `tool_router()` constructor function on that type.

Options the writing-plans step should pick from:

1. **Single big struct** (`KdeMcp`) with all 15 tools as `#[tool]` methods in one or more `#[tool_router]` `impl` blocks. Per-tool modules become free helper functions (`fn observe_impl(state: &State, …) -> Result<…>`) called from the `#[tool]` method bodies. The `src/tools/` directory still maps 1:1 to files; it just contains plain functions, not tool-trait impls.
2. **Multiple `#[tool_router]` impls** on the same struct, one per source file via Rust's `impl Foo { … }` repetition. The macro must support this; from the examples it appears to (there are nested files with shared state). Verify in the Phase 0 spike.
3. **Router composition**. The `ToolRouter<Self>` type is constructible directly; if the proc-macro doesn't compose, fall back to building a router by hand. Less ergonomic but matches the spec's per-file decomposition more cleanly. Treat as a fallback.

The structured-error type is `rmcp::ErrorData` (re-aliased as `McpError` in the examples). The spec's §8 error taxonomy needs to map onto `McpError` constructors (`resource_not_found`, etc., are visible in the example). The error catalogue should be implemented as `impl From<crate::error::KdeMcpError> for McpError`.

### Concrete idioms worth copying

- **Parameters extraction**: `Parameters(MyArgs { a, b }): Parameters<MyArgs>` is the macro-supported pattern. `MyArgs` must derive `Deserialize` + `schemars::JsonSchema`.
- **Long-running tools**: `#[tool(description = "…", execution(task_support = "optional"))]`. There is a built-in `task_manager::OperationProcessor`. This is relevant to the spec's `wait` and `bash` tools — they can opt into the task protocol for cancellation.
- **Request context**: handlers can take `ctx: RequestContext<RoleServer>` to access extensions, including HTTP request parts. For stdio mode this is mostly noise; useful if/when we add a transport.
- **Trait surface**: the `ServerHandler` trait now requires `get_info()` returning `ServerInfo` with `with_server_info(Implementation::from_build_env())`. Cargo metadata is read at compile time.

### Risk callouts

- The spec's §5.1 line "`rmcp = "0.1"`" is dead. Bump to `1` (or pin `1.7.0`) in the plan. Treat the cargo dep line as a 6-line patch.
- `ProtocolVersion::V_2024_11_05` is the version the counter example uses; the **spec talks about MCP 2025-06-18**. There is a `V_2025_06_18` (or similar) in the model module — confirm in the spike. If it's not present, that's a real blocker: we can't claim to implement the 2025-06-18 spec without the protocol-version constant.
- `task_handler` is a separate proc-macro; cancellation lives in `task_manager::OperationProcessor`. The spec's "cancel via KGlobalAccel + broadcast `CancellationToken`" still works, but it would coexist with rmcp's own task model. Pick one or document the layering.
- The default `tracing_subscriber` setup in the example writes to stderr with `with_ansi(false)`. This matches the spec's §5.3 step 6 ("Print one-line startup banner on stderr"). Good — no change needed.

## 2 — `reis 0.6.1`

### Verified facts

- **Version**: 0.6.1 (published 2026-02-17 per crates.io).
- **Repo**: https://github.com/ids1024/reis (default branch `master`).
- **License**: MIT.
- **MSRV**: 1.71.1.
- **Description (crates.io)**: "Pure Rust implementation of libei/libeis protocol."
- **Features**: `tokio` (enables `tokio` + `futures-util`), `async-io`, `calloop` (experimental).
- **Examples**: `list-devices.rs` (tokio), `receive.rs` (tokio), `receive-synchronous.rs`, `type-text.rs` (calloop), `reis-demo-server.rs` (calloop).
- **Project status (README)**: "API is still subject to change."

### The current minimal sender bootstrap (tokio)

Drawn from `examples/list-devices.rs`. The relevant skeleton:

```rust
use futures_util::StreamExt;
use reis::{ei, tokio::EiEventStream, PendingRequestResult};

async fn open_connection() -> ei::Context {
    if let Some(context) = ei::Context::connect_to_env().unwrap() {
        context
    } else {
        // … portal-based fallback via ashpd; for KDE we use the
        //   org.kde.KWin.EIS.RemoteDesktop fd directly instead.
        unreachable!("kde-mcp gets fd from KWin EIS, not the portal")
    }
}

#[tokio::main(flavor = "current_thread")]
async fn main() {
    let context = open_connection().await;
    let mut events = EiEventStream::new(context.clone()).unwrap();

    let handshake_resp = reis::tokio::ei_handshake(
        &mut events,
        "kde-mcp",
        ei::handshake::ContextType::Sender,
    ).await.unwrap();

    while let Some(result) = events.next().await {
        let event = match result.unwrap() {
            PendingRequestResult::Request(e) => e,
            PendingRequestResult::ParseError(_) => continue,
            PendingRequestResult::InvalidObject(_) => continue,
        };
        // … dispatch on ei::Event::Connection / Seat / Device / Keyboard
    }
}
```

A simpler shape using `Context::handshake_tokio` (from `examples/receive.rs`):

```rust
let (_connection, mut events) = context
    .handshake_tokio("kde-mcp", ei::handshake::ContextType::Sender)
    .await
    .unwrap();
```

`handshake_tokio` returns `(ei::Connection, EiEventStream)` and is the cleaner of the two paths. The event type after that point is `reis::event::EiEvent` (a higher-level enum like `SeatAdded`, `DeviceAdded`, `KeyboardKey`, …), not the raw `ei::Event::*` protocol variants. **Picking which event surface to consume is a design choice the implementation plan must make.** The high-level `EiEvent` enum is easier; the raw protocol variants give more control over capability binding.

### Key API facts

- **`ei::Context::connect_to_env()`** — checks `LIBEI_SOCKET`. **For kde-mcp this is not the path we take**; we receive an FD from `org.kde.KWin.EIS.RemoteDesktop`. The conversion is `let stream = std::os::unix::net::UnixStream::from(fd); let context = ei::Context::new(stream).unwrap();` (visible in every example's portal fallback). So `src/kwin/eis.rs` will: D-Bus call → `OwnedFd` → `UnixStream::from(fd)` → `ei::Context::new(stream)`.
- **`ei::handshake::ContextType::Sender`** vs `Receiver` — we want `Sender` (we inject; we don't receive captured events).
- **Capability binding** — the spec talks about "init reis context". In current reis, on `EiEvent::SeatAdded` you call `evt.seat.bind_capabilities(DeviceCapability::Pointer | DeviceCapability::PointerAbsolute | DeviceCapability::Keyboard | DeviceCapability::Button | DeviceCapability::Scroll)`. Touch capability is `DeviceCapability::Touch` (spec doesn't need it but it's available).
- **Key injection** — `keyboard.key(keycode, ei::keyboard::KeyState::Press)`, then `device.frame(serial, time)`, then `keyboard.key(…, KeyState::Released)`. Keycodes are evdev-style **minus 8** (visible in `type-text.rs`). xkb-to-keycode mapping is the caller's responsibility — `xkbcommon` crate is the realistic dependency.
- **Pointer motion** — not shown in the examples; `ei::pointer::Pointer` has `motion_relative(dx, dy)` and `ei::pointer_absolute::PointerAbsolute` has `motion_absolute(x, y)`. Verify exact method names in the spike.

### What spec §13 should change

- `src/kwin/eis.rs` is still the right home. Inside it, the flow is:
  1. `zbus` call `org.kde.KWin.EIS.RemoteDesktop` → `OwnedFd`
  2. `UnixStream::from(fd)` → `ei::Context::new(stream)`
  3. `context.handshake_tokio("kde-mcp", ContextType::Sender)` → `(Connection, EiEventStream)`
  4. Spawn a tokio task that consumes `EiEventStream`, binds capabilities on `SeatAdded`, and stores the keyboard / pointer / pointer-absolute handles in a shared state.
  5. Expose a small API to `src/tools/{mouse,keyboard}.rs`: `inject_key(KeySym)`, `move_pointer(dx, dy)`, etc.
- The `xkbcommon` crate is implied. Add it to the Cargo deps. The spec doesn't list it; the writing-plans step should add it explicitly.

### Risk callouts

- The reis README says the API is still subject to change. For a personal-use project this is acceptable, but: **pin `reis = "=0.6.1"` exactly**, not `"0.6"`. A minor bump might rename `EiEventStream`.
- `handshake_tokio` was added relatively recently (the older `reis::tokio::ei_handshake(&mut events, …)` free function is also still present per `list-devices.rs`). Either works; prefer `handshake_tokio` for ergonomics.
- The `calloop` examples (`type-text.rs`, `reis-demo-server.rs`) are richer than the tokio ones but require a calloop event loop. We're tokio-only per ADR-0001, so we won't use them as reference. Read them only for the protocol-level dispatch logic.
- The crate has 31 GitHub stars and "4 open issues, 5 open PRs". This is a small library. Expect to read the source when something doesn't match the README. The author (`ids1024`) is the same as the maintainer of `cosmic-comp`'s input layer — competent, but bus-factor of 1.
- The spec's §5.6 line "One `reis::Context`" is correct in name. Add: "Plus a long-lived `EiEventStream` consumer task and a shared `Arc<EiState>` for the bound capabilities."

## 3 — `atspi 0.30.0`

### Verified facts

- **Version**: 0.30.0 (published 2026-05-06 per crates.io).
- **Repo**: https://github.com/odilia-app/atspi
- **Subcrates**: `atspi-common 0.14.0`, `atspi-connection 0.14.0`, `atspi-proxies 0.14.0`. The umbrella `atspi` crate re-exports them.
- **Default features**: `connection`, `proxies`, `p2p`, `wrappers`.
- **Optional features**: `tokio`, `tracing`. (The spec already calls out `tokio` — keep it.)
- **Examples**: `accessible-counts.rs`, `bus-tree.rs`, `currently-focused-frame.rs`, `focused-smol.rs`, `focused-tokio.rs`, `p2p-tree.rs`, `selected-text.rs`, `text-under-click.rs`.

### The current minimal connect-and-walk shape

From `examples/currently-focused-frame.rs`:

```rust
use atspi::State;
use atspi_connection::set_session_accessibility;
use atspi_proxies::accessible::ObjectRefExt;

#[tokio::main]
async fn main() -> Result<(), Box<dyn Error>> {
    let atspi = atspi::AccessibilityConnection::new().await?;
    let conn = atspi.connection();
    set_session_accessibility(true).await?;

    let apps = atspi.root_accessible_on_registry().await?.get_children().await?;
    for app in apps.iter() {
        let proxy = app.clone().into_accessible_proxy(conn).await?;
        for frame in proxy.get_children().await? {
            if frame.is_null() { continue; }
            let frame = frame.clone().into_accessible_proxy(conn).await?;
            if frame.get_state().await?.contains(State::Active) {
                println!("Active: {}", frame.name().await?);
            }
        }
    }
    Ok(())
}
```

The key types — verified by name in the example imports — are:

- **`atspi::AccessibilityConnection`** — entry point. **The spec's name (§5.3 step 5) is correct.** Construct with `AccessibilityConnection::new().await?`.
- **`atspi::AccessibilityConnection::connection()`** — returns `&zbus::Connection`. Pass this to anything that wants the underlying bus.
- **`atspi::AccessibilityConnection::root_accessible_on_registry()`** — returns an `AccessibleProxy` to the registry root. This is the canonical tree entry point.
- **`atspi_proxies::accessible::AccessibleProxy<'_>`** — the per-node proxy. Methods: `get_children()`, `get_role()`, `get_state()`, `name()`, `get_application()`, `child_count()`.
- **`atspi::ObjectRefOwned`** / `ObjectRef` — the lightweight reference type returned by `get_children()`. Lift to a proxy via `child.into_accessible_proxy(conn)` or `child.as_accessible_proxy(conn)` (the latter doesn't consume).
- **`atspi_proxies::accessible::ObjectRefExt`** — extension trait that adds `.into_accessible_proxy()` / `.as_accessible_proxy()` on `ObjectRef`. **Must be in scope** (`use atspi_proxies::accessible::ObjectRefExt`).
- **`atspi_proxies::proxy_ext::ProxyExt`** — extension trait that lets an `AccessibleProxy` give you sibling proxies: `.proxies().await?.component()`, `.text()`, `.action()`, etc. Visible in `text-under-click.rs`.
- **`atspi::State`** — bitmask flag set (`Active`, `Focused`, `Showing`, `Visible`, …).
- **`atspi_connection::set_session_accessibility(true)`** — turns on AT-SPI for the session. Spec's §5.4 step 7 talks about setting `IsEnabled=true` on `org.a11y.Status` — this helper does exactly that. Use it instead of hand-rolling.

### Event stream (for the `wait` tool)

From `examples/focused-tokio.rs`:

```rust
let atspi = atspi::AccessibilityConnection::new().await?;
atspi.register_event::<ObjectEvents>().await?;
let events = atspi.event_stream();
tokio::pin!(events);
while let Some(Ok(ev)) = events.next().await {
    let Ok(change) = <StateChangedEvent>::try_from(ev) else { continue };
    if change.state == "focused".into() && change.enabled { /* … */ }
}
```

The shape is: register the event group → consume the stream → narrow each event with `try_from` to the specific event type you care about. This is the right primitive for the spec's `wait` tool (§6.1): subscribe to `ObjectEvents`, filter for `StateChangedEvent { state: "focused" | "showing", enabled: true }`, return on match or timeout.

### What spec §13 should change

- `src/atspi/connection.rs` — keep the name. The contents are essentially `AccessibilityConnection::new().await?` plus `set_session_accessibility(true).await?`.
- `src/atspi/tree.rs` — implementation is `root_accessible_on_registry()` → recursive `get_children().await` → `into_accessible_proxy()`. Use the `bus-tree.rs` algorithm (uses a `Vec<AccessibleProxy>` work-queue stack, not recursion, to dodge the async-recursion problem). **Lift the queue-based tree walk from `bus-tree.rs` verbatim — it's the most efficient pattern we'll find.**
- `src/atspi/ref_encoding.rs` — the spec assumed we mint our own ref strings from atspi object paths. Current atspi has `ObjectRef` (a struct with bus name + path). The opaque-ref encoding the spec describes wraps this. No rename needed; the implementation will be `Base64(serde::to_bytes(&ObjectRefOwned))`.

### Concrete idioms worth copying

- **Reaching sibling interfaces** (the spec's `act_on_element` will need this — clicking via the Action interface, reading text via the Text interface):
  ```rust
  use atspi_proxies::proxy_ext::ProxyExt;
  let text_proxy = accessible_proxy.proxies().await?.text().await?;
  let component_proxy = accessible_proxy.proxies().await?.component().await?;
  ```
- **State checks** (the spec's `wait` tool needs `Showing`, `Visible`, `Focused`):
  ```rust
  let s = proxy.get_state().await?;
  if s.contains(State::Showing) && s.contains(State::Visible) { … }
  ```
- **`CoordType`** — `atspi::CoordType::Screen` / `Window` matters for `Component::contains(x, y, …)`. Visible in `text-under-click.rs`.

### Risk callouts

- atspi 0.x is pre-1.0; the project has gone 0.22 → 0.30 in roughly a year. **Pin `atspi = "=0.30.0"`** (and `atspi-common`, `atspi-connection`, `atspi-proxies` as transitive locks). A 0.31 minor could shift trait bounds.
- The spec's `act_on_element` tool needs the `Action` interface for invoking ("primary action"). That's `accessible_proxy.proxies().await?.action().await?` then `action_proxy.do_action(0)` or `.get_action_name(0)`. Verify the exact method names against `atspi-proxies/src/action.rs` in the spike — none of the read examples shipped exercises Action.
- The spec uses `atspi::AccessibilityConnection`. **Confirmed: the type still exists by that name.** Some interim 0.2x release renamed things; 0.30 has it back to `AccessibilityConnection`. No change required to §5.3 step 5.
- The `p2p` feature is on by default and enables direct peer-to-peer accessibility connections (skip the registry for known endpoints). We probably don't need it; it's harmless on by default.

## 4 — Supporting crates audit

**`zbus 5.15.0`** (2026-04-26). The spec assumes 5.15.0 exactly; that's the current. No work needed. zbus 5.x has stable `Connection`, `Proxy`, `dbus_proxy!` macro. The KWin Scripting / ScreenShot2 / EIS clients in `src/kwin/*` are straight zbus proxy macros. Note: zbus's tokio integration requires the `tokio` feature explicitly; the default is async-std. Make sure `Cargo.toml` has `zbus = { version = "5.15", default-features = false, features = ["tokio"] }`.

**`notify-rust 4.17.0`** (2026-05-04). The spec uses this for D-Bus `org.freedesktop.Notifications` calls (approval prompts, lock events). API is stable since 4.x; `Notification::new().summary().body().show_async().await` works as before. MSRV 1.63.0 is comfortable. No risk.

**`portable-pty 0.9.0`** (2025-02-11). Stable since well before the spec was written. The spec's `src/util/pty.rs` pattern (`native_pty_system()`, `slave.spawn_command()`, `master.try_clone_reader()`, `master.take_writer()`) is unchanged. Note: portable-pty's master is **not** tokio-async out of the box; the spec correctly notes this needs a blocking thread + channel or `tokio::task::spawn_blocking`. Confirmed against current README; no surprises.

**`fd-lock 4.0.4`** (2025-03-10). The spec uses fd-lock for the single-session lockfile in `src/lock.rs`. API: `RwLock::new(file)`, `.write()?` returns a guard. Stable; no changes from spec's mental model.

## 5 — What to send to writing-plans

The plan-author should treat the following as **Phase 0 spike tasks**, before any real implementation work:

1. **Confirm `ProtocolVersion::V_2025_06_18` exists in `rmcp::model`**, or vendor the constant. If not present, the spec's claim of MCP 2025-06-18 conformance is provisional. (~10 min.)
2. **Verify that multiple `#[tool_router]` `impl` blocks on the same struct compose** so the spec's per-file `src/tools/` layout survives. If not, pick a fallback (single file with all tools, or hand-built router). (~30 min — write a 2-file toy.)
3. **Verify atspi-proxies `Action` proxy method names** (`do_action`, `get_action_name`, `n_actions`) by reading `atspi-proxies/src/action.rs`. The `act_on_element` tool depends on this. (~10 min, read-only.)
4. **Verify reis pointer-absolute method names** (`motion_absolute`, expected on `ei::pointer_absolute::PointerAbsolute`). Not exercised by any committed example; must be read from `src/pointer_absolute.rs`. (~15 min, read-only.)
5. **xkbcommon dependency**: confirm `xkbcommon 0.7+` is current and usable for keysym→keycode mapping. The spec doesn't list it; the plan must.

### Module-name changes the plan should make against spec §13

| Spec module | Current API | Change |
|---|---|---|
| `src/tools/*.rs` (each a separate "tool") | one struct with `#[tool]` methods | **Keep file layout, change semantics**: each `src/tools/<name>.rs` becomes a free-function module that the central `KdeMcp` struct's `#[tool]` method delegates to. The `#[tool]` annotation itself lives in `src/lib.rs` or `src/server.rs` on the umbrella impl. |
| `src/atspi/connection.rs` | `atspi::AccessibilityConnection::new()` + `set_session_accessibility(true)` | No rename. Note that `set_session_accessibility` is in `atspi-connection`, not the umbrella crate. |
| `src/kwin/eis.rs` | `org.kde.KWin.EIS.RemoteDesktop` → `OwnedFd` → `UnixStream::from(fd)` → `ei::Context::new(stream)` → `context.handshake_tokio("kde-mcp", Sender)` | No rename. Add an `eis_state.rs` sibling for the long-lived `Arc<EiState>` (bound seat + keyboard + pointer handles). |
| `src/refs.rs` | wraps `atspi::ObjectRefOwned` | No rename. Body is `Base64(serde_cbor(ObjectRefOwned + nonce + timestamp))`. |

### Stability verdict

- **rmcp 1.7.0** — looks 1.0-quality. The major-version jump did the API rewrite that 0.x churn implied; further breakage in 1.x should be additive. Use freely.
- **atspi 0.30.0** — pre-1.0 but the API surface that kde-mcp touches (`AccessibilityConnection`, `AccessibleProxy::{get_children, get_state, name, get_role}`, `ObjectRefExt`) has been stable across the last several 0.x releases. Pin exactly; expect to bump every 3–6 months and re-test.
- **reis 0.6.1** — actively evolving, one-maintainer, README admits API instability. Pin exactly. Plan for one bring-up break per year. Acceptable for a personal-use tool.

### What I could not verify and which writing-plans should mark as risk

- Exact reis pointer-absolute / pointer-relative method names (read from source in the spike).
- Whether `#[tool_router]` supports multiple `impl` blocks on one type (spike test).
- Whether `ProtocolVersion::V_2025_06_18` is exported from `rmcp::model` (spike).
- atspi-proxies `Action` interface method names (read from source in the spike).
- KWin's `org.kde.KWin.EIS.RemoteDesktop` exact method signature in current Plasma 6 — verify against the live system via `qdbus6` before encoding the proxy macro.
